# 개발 구조 검토 — 기능 통합과 Windows 실행 제어

> 검토일: 2026-09-13
> 코드와 실행 스크립트를 검토한 설계 제안입니다. 서버 시작·종료, 실제 발송, 데이터 이전은 실행하지 않았습니다.
> 후속 저장본에서 선택 1·2·3·6번과 아침 07:30·저녁 21:00을 확인했습니다. 구현 현황은 [IMPLEMENTATION.md](IMPLEMENTATION.md)를 참고하세요.

## 1. 추천 결론

**portfolioweb의 필요한 기능을 only의 기존 FastAPI 백엔드에 단계적으로 통합하는 방식이 더 타당합니다.**

현재 only는 자체 FastAPI를 사용합니다. 앞선 문서의 “portfolio 기능 활용”은 코드 재사용을 뜻하며, 별도 portfolio 서버를 반드시 실행해야 한다는 의미는 아닙니다.

- 운영 기준 데이터: only의 `family-assets.db`.
- 기능 구현: 선택한 분석·알림 코드를 only의 데이터 모델과 가족 권한에 맞게 이식.
- 실행 구성: 기존 Next.js 화면 + only FastAPI 유지. portfolio 서버를 필수 구성으로 추가하지 않음.
- 기존 portfolio 프로젝트와 DB: 이전·검증 기간에 보존. 필요한 기존 메모·관심종목·재무 이력만 선별 이전.
- Windows 사용: 앱에서 자동 작업을 켜고 끄고, 바탕화면 바로가기로 앱 전체를 시작·종료·재시작.

## 2. 두 방식 비교

| 판단 항목 | only에 필요한 기능 통합 — 추천 | portfolio를 별도 API로 운영 |
|---|---|---|
| 실행 관리 | 기존 화면·백엔드 한 묶음 유지 | portfolio 서버와 상태 감시·재시작 관리 추가 |
| 자산 데이터 | only 데이터로 분석·알림 일원화 | 현 API는 portfolio DB를 조회하므로 ID 매핑·동기화 또는 API 재설계 필요 |
| 가족 권한 | only의 관리자·가족 조회 규칙 활용 | 서비스 사이 인증과 가족별 데이터 범위 전달 필요 |
| 알림 | 한 곳에서 예약·중복·발송 이력 관리 | 양쪽 발송 책임과 중복 방지 기준을 별도로 정해야 함 |
| 개발 비용 | 초기 모델 변환과 기능 이식 필요 | 호출 연결 외에 데이터 동기화·프로세스 제어까지 필요 |
| 장애 영향 | 분석 기능은 같은 백엔드에 있으므로 작업 격리·시간 제한 필요 | 분석 서버 장애를 격리할 수 있으나 연결 실패 대응 필요 |
| 적합한 상황 | 개인 Windows PC에서 only를 주 앱으로 사용 | 두 앱을 계속 독립 개발하거나 여러 앱이 공통 분석 서버를 사용할 때 |

## 3. 코드에서 확인한 판단 근거

1. **기술 기반이 같습니다.** 양쪽 requirements의 FastAPI·Uvicorn·SQLAlchemy·httpx·yfinance 고정 버전이 같습니다. 선택 기능을 같은 백엔드에 옮길 기반은 갖춰져 있습니다. 실제 의존성 호환성은 이식 후 검증해야 합니다.
2. **현재 API는 portfolio 데이터에 묶여 있습니다.** `/api/holdings/{holding_id}/fundamentals` 등은 portfolio DB에서 해당 ID를 먼저 찾습니다. only의 종목 ID를 그대로 보내는 것으로는 연결되지 않습니다.
3. **같은 이름의 holdings 테이블도 구조가 다릅니다.** only는 `owner`, `name`, `principal`을 사용하고, portfolio는 `member_slug`, `company_name`, `principal_amount` 및 엑셀 원본 필드를 사용합니다. 두 앱에 동일 DB 파일을 지정하는 방식은 적절하지 않습니다.
4. **실행 설정도 분리되어 있습니다.** portfolio는 시작 시 조건에 따라 엑셀을 재적재하며, Windows에서는 자체 `data/portfolio.db`를 사용하도록 설정 코드가 구성되어 있습니다.
5. **only에는 이미 실행 관리의 기초가 있습니다.** `serve.mjs`가 Next.js 3000번과 FastAPI 8000번을 함께 실행합니다. 설치 스크립트에는 선택적으로 Windows 로그인 시 자동 실행을 등록하는 기능이 있습니다. 실제 PC의 등록 여부는 이번에 확인하지 않았습니다.

## 4. 명령어 없이 켜고 끄는 방식

### 앱 내부: 자동 작업 제어

관리자 설정에 아래 항목을 추가하는 방식을 제안합니다. 실제 포함 항목은 사용자가 선택한 기능에 맞춥니다.

| 화면 항목 | 버튼·설정 | 동작 |
|---|---|---|
| 일일 브리핑 | 켜기/끄기, 시간, 미리보기, 지금 보내기 | 예약 발송 제어 |
| 가격 알림 | 켜기/끄기, 확인 주기 | 목표가·손절가 등 선택 조건 감시 |
| 뉴스·공시 알림 | 켜기/끄기, 요약 주기 | 새 항목 수집·발송 제어 |
| 자동 시세 갱신 | 켜기/끄기, 실행 시간 | 현재 환경 변수 설정을 화면에서 변경 |
| 작업 상태 | 다음 실행, 최근 성공·실패, 재시도 | 문제가 생겨도 명령창 없이 확인 |

- 설정은 DB에 저장하고 재시작 후에도 유지합니다. 현재 스케줄은 시작 시 환경 변수에서 읽으므로 실행 중 변경 기능이 필요합니다.
- 끄기는 이후 예약 실행과 미발송 작업을 중지하는 의미로 정의합니다. 이미 외부로 전송한 메시지는 되돌릴 수 없습니다.
- 자동 작업을 꺼도 자산 조회·가계부·일정 화면은 계속 사용할 수 있게 합니다.
- 무거운 분석은 웹 요청과 분리된 작업으로 실행하고 시간 제한·실행 이력을 둡니다. 별도 분석 서버가 필요한지는 실제 부하를 보고 판단합니다.

### Windows: 앱 전체 제어

바탕화면에 **모아 시작 / 모아 종료 / 모아 재시작 / 모아 열기** 바로가기를 제공하는 구성이 적절합니다.

- 기존 PowerShell·Node 실행 코드를 감싼 실행 도구를 만들고, 사용자는 바로가기만 누릅니다.
- 실행 여부·준비 완료를 확인해 중복 실행을 막고, 백그라운드 실행 결과와 로그를 남깁니다.
- 종료 시 앱이 관리하는 프로세스인지 확인하고 정상 종료를 먼저 시도합니다.
- 현재 자동 실행 코드는 **Windows 로그인 후** 실행하는 방식입니다. 로그인 전부터 서비스가 필요하면 Windows 서비스 구성을 별도로 검토합니다.
- **앱 전체가 꺼지면 웹 화면도 열리지 않으므로 그 화면의 버튼으로 다시 켤 수 없습니다.** 완전 종료 후 시작은 Windows 바로가기 또는 앱 밖에서 동작하는 실행 관리자가 담당해야 합니다.
- PC 전원 꺼짐·절전 중에는 이 PC의 예약 발송도 실행되지 않습니다.

## 5. 별도 API를 유지한다면 필요한 작업

두 앱을 계속 독립적으로 사용할 계획이라면 only에서 portfolio의 시작·중지·재시작 버튼을 제공하는 것도 가능합니다. 다만 아래 작업까지 포함해야 합니다.

- portfolio를 only 백엔드와 다른 내부 포트(예: 8001)로 실행.
- 관리자만 고정된 서비스의 시작·중지·재시작을 요청하도록 하고, 임의 명령어 실행 API는 만들지 않음.
- 실행 관리자가 프로세스 소유권·상태·준비 완료를 확인하고 중복 실행·비정상 종료를 처리.
- only가 종료되어도 portfolio를 유지할지 함께 종료할지 정하고, 재시작 시 기존 프로세스와 다시 연결.
- 가족별 권한을 확인하는 only를 통해 호출하고, portfolio와의 내부 인증을 추가.
- only의 데이터 전달형 분석 API로 바꾸거나, 종목 ID 매핑과 데이터 동기화 규칙을 구현.
- 시세 갱신·텔레그램 예약과 실제 발송을 어느 앱이 담당할지 하나로 지정.

현재 목표에서는 이 운영 코드보다 선택 기능을 only에 옮기는 작업의 효용이 더 큽니다.

## 6. 권장 진행 순서

1. 저장된 `o` 표시를 확인해 개발 범위 확정.
2. Windows 바로가기와 앱 내부 자동 작업 설정·상태 화면 마련.
3. 선택한 기능을 only 데이터·권한·발송 이력에 맞춰 순차 이식.
4. 가족별 데이터 범위, 알림 중복, 재시작 후 설정 유지, 작업 실패 복구 검증.
5. 필요한 portfolio 기존 데이터를 백업 후 선별 이전하고 결과 확인.
6. only만 실행한 상태에서 선택 기능의 동작을 검증한 뒤 기존 portfolio 상시 실행 필요성을 재평가.
